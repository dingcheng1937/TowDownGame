### 二、发现的问题

按严重程度从高到低排列。

---

#### 问题 1：入口索引严重不完整（高优先级）

`docs/README.md` 作为文档入口，**缺少两个完整子目录和多个重要文件的引用**：

**缺失的目录**:
- ❌ `prd/`（3 个 PRD 文件）完全未提及
- ❌ `gdd/`（2 个文件，含系统架构图）完全未提及

**缺失的重要文件**:
- `architecture/inventory-system.md` — 背包系统分析
- `architecture/inventory-equip-ui.md` — 装备/仓库 UI 实现
- `architecture/correction-center-v2-architecture.md` — 矫正中心 V2 架构
- `architecture/correction-survival-architecture.md` — 矫正生存系统架构
- `guides/godot-ui-pattern.md` — UI 实现模式指南
- `guides/Godot-UI-Complete-Guide.md` — UI 完整指南
- `planning/expansion-analysis.md` — 拓展方向分析（README 有目录但表格缺这件）

**影响**: 新开发者无法从入口导航到全部文档。

---

#### 问题 2：重复内容（中优先级）

**P2a**: `class-diagram.mermaid` 的内容与 `system_design.md` 第 3 节的数据结构类图**完全一致**（同一份 BaseLoot / MeleeWeaponPickup / EventBus 类图，连注释文字都相同）。

**P2b**: `sequence-diagram.mermaid` 的内容与 `system_design.md` 第 4 节的四个时序图**完全一致**（近战拾取 / 警戒阈值 / 投掷物 HUD / 理智氛围，相同的参与者名称和流程）。

**影响**: 两个独立的 `.mermaid` 文件缺少出处说明，容易导致不同步。对 `system_design.md` 的修改需要同步到这两个文件，增加了维护负担。

---

#### 问题 3：GYM 模块数量多处不一致（中优先级）

| 来源 | 声称数量 | 实际 GYM 范围 |
|------|---------|--------------|
| `docs/README.md` GYM 对照表 | 12 个 | GYM_01 ~ GYM_12 |
| `docs/gym/README.md` | 12 个 | GYM_01 ~ GYM_12 |
| `docs/planning/project-evaluation.md` | 10 个 | GYM_01 ~ GYM_10 |
| 实际 demo/ 目录 | — | GYM_01 ~ GYM_16 |

项目实际有 **16 个 GYM 模块**（GYM_01 ~ GYM_16），其中：
- GYM_13: ButtonCounter / CorrectionCenter（两个版本？需验证）
- GYM_14: HealthDemo
- GYM_15: CorrectionCenter
- GYM_16: CorrectionSurvival

所有文档中对 GYM 总数的描述都已过时。

---

#### 问题 4：过时信息 / 内容失准（中优先级）

**P4a**: `planning/project-evaluation.md` 描述 "已在 Steam 上架（App ID: 2153420），项目名称《Don't Stop》"。这似乎是原项目的历史信息，与当前 `TowDownGame` 项目的定位（诡异搜打撤/精神矫正中心）不一致。该文档可能需要重写或标记为"历史参考"。

**P4b**: `planning/project-evaluation.md` 引用 `RESOLUTION_SCHEME.md`（大写），但实际文件名为 `architecture/resolution-scheme.md`（小写 kebab-case）。链接失效。

**P4c**: `planning/weird-loot-shooter-plan.md` 中的理智系统设计代码（`PlayerData.gd` 扩展方案）已是过时草图，实际已实现独立的 `SanityServer` autoload。

**P4d**: `planning/expansion-analysis.md` 中的存档/成就/状态机/行为树代码是通用伪代码片段，不是基于当前项目实际代码库的描述。

---

#### 问题 5：版本时间线断层（低优先级）

文档创建时间跨越 **1 年**:

| 日期 | 文件 |
|------|------|
| 2025-07-09 | `system_design.md` |
| 2025-07-15 | `prd/correction-center-increment.md` |

---

#### 问题 6：归档文档缺乏归属说明（低优先级）

根目录的 `class-diagram.mermaid` 和 `sequence-diagram.mermaid` 放在 `system_design.md` 所在层级，但实际上是该文档的内嵌图表的**外置副本**。缺乏元数据说明它们与 `system_design.md` 的从属关系。类似问题见于 `gdd/system-architecture.mermaid` 与 `architecture/` 目录的关系。

### 三、已有的良好实践

1. **目录分类清晰**: `architecture/` / `features/` / `prd/` / `gdd/` / `guides/` 的细分是合理的，PRD→架构→实现的分层结构清晰。
2. **`NARRATIVE_DESIGN.md` 质量高**: 叙事设计的 Tier 分层、角色语音柱石、Banned Retcons 等结构为后续内容写作提供了优秀模板。
3. **`gdd/gameplay-systems-and-balance.md`** 的设计支柱+验证问题的写法兼顾了设计理念和可验证性。
4. **`prd/correction-center-increment.md`** 的审计结论（TL;DR）直接标注了"已有大量实现，聚焦差距分析"，明确了自己的定位。
5. **`gym/` 子目录自成体系**: GYM 列表、计划、测试报告、UI 分析四份文档相互配合，结构完整。

### 阶段五：长期维护建议

1. **建立文档版本注释规范**: 每次修改文档时，在文件末尾或顶部 `> 最后更新: YYYY-MM-DD` 标注修改日期。
2. **引入文档同步检查点**: 当新增 GYM 模块或核心系统时，同步更新 `docs/README.md` 和 `docs/gym/README.md` 的索引。
3. **归档机制**: 对于明确被替代的文档（如 V1 设计），移到 `docs/archive/` 子目录并保留索引中的跳转链接，而不是直接删除。
4. **`.mermaid` 文件管理**: 如果 mermaid 图是某个 .md 文件的派生副本，用文件顶部注释标明来源；如果是从多个 .md 汇总的"总览图"，注释应列出所有来源文件。
